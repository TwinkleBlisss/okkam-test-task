# Тестовое задание Okkam

API, вычисляющее процент вхождения одной аудитории в другую по
среднему Weight респондентов.

## Запуск

```bash
docker compose up
```

БД создаётся и наполняется сама
(`init-data/`), API стартует после готовности БД и слушает **80-й порт**.

### Проверка

#### Curl
```bash
curl "http://localhost/getPercent?audience1=Age%20BETWEEN%2018%20AND%2035&audience2=Sex%20=%202%20AND%20Age%20%3E=%2018"
```

#### Swagger
http://0.0.0.0:80/docs


## API

`GET /getPercent?audience1=...&audience2=...` — аудитории в формате
SQL-синтаксиса по колонкам `age`/`sex` (без подзапросов и функций),
ответ `{"percent": float}` в диапазоне 0..1.

| Status Code | Reason |
|-----|-------|
| 200 | успех |
| 422 | недопустимый фильтр |
| 500 | ошибка БД |

Крайние случаи:

- идентичные аудитории → `1.0`;
- не пересекаются → `0.0`;
- первая подмножество второй → `1.0`;
- первая аудитория пуста → `0.0`.

## Структура проекта

- **app/** — основное приложение:
  - `main.py` — настройка и запуск FastAPI.
  - `api.py` — эндпоинты `/getPercent` и `/health`.
  - `service.py` — бизнес-логика (расчёт процентов).
  - `schemas.py` — Pydantic-модели и валидация данных.
  - `db.py` — подключение к БД и SQL-запросы.
  - `exceptions.py` — кастомные исключения и обработчики ошибок.
  - `logger.py` — настройка логирования.
  - `config.py` — настройки приложения и подключения к БД.

- **init-data/** — SQL-скрипты для подготовки БД:
  - `01-schema.sql` — создание таблицы `statistics`.
  - `02-copy.sql` — загрузка 500 000 строк из CSV.
  - `03-respondent_agg.sql` — создание агрегированной таблицы.

- **tests/** — тесты:
  - `test_schemas.py` — проверка валидации данных.
  - `test_api.py` — тестирование API без подключения к БД.

## Ключевые моменты

- **`respondent_agg`** — так как задача предполагает вычисление  avg(weight) по каждому респонденту, я решил заранее сгруппировать данные по ним, чтобы затем можно было работать с уменьшенным объёмом данных (17k строк вместо 500k).

- **Итоговое вычисление сумм** первой аудитории и пересечения происходит за 1 запрос к таблице `respondent_agg` через ```SUM(avg_weight) FILTER ...```

- По ТЗ в качестве параметров запроса нам передают фрагмент SQL, значит было бы неплохо **проверять этот код**. Для этой задачи я выбрал библиотеку **sqlglot**. Она проверяет:
  - целостность WHERE-запроса через подстановку в SELECT;
  - отсутствие нескольких SQL-операций;
  - отсутствие подзапросов в WHERE;
  - отсутствие вызовов встроенных SQL-функций;
  - отсутствие обращений к недопустимым полям и таблицам.

- **Кеш** - решил сделать самым простым способом (через lru_cache). Повесил этот декоратор отдельно на `валидацию` (check_where_clause) и `на запрос в БД` (cached_audience_sums). Допускаю, что реализация не самая лучшая, но решил оставить так.
