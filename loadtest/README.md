# Нагрузочное тестирование (Locust)

Нагрузочный тест `GET /getPercent` и `GET /health`. Фреймворк —
[Locust](https://locust.io) (добавлен в dev-зависимости: `uv sync`).

## Сценарии

`locustfile.py` генерирует воспроизводимый (seed=42) пул из ~70 пар
`(audience1, audience2)`, покрывающий разные условия запроса:

| лейбл | условие |
|-------|---------|
| `age_eq` | точный возраст: `Age = N` |
| `age_range` | интервал: `Age BETWEEN a AND b` |
| `age_bounds` | границы: `Age >= N` / `Age <= N` |
| `sex` | пол: `Sex = 1` / `Sex = 2` |
| `combined_and` | пересечение: `Sex = s AND Age BETWEEN ...` |
| `or_cond` | объединение: `Sex = s OR Age >= N` |
| `long_or` | длинное OR-условие, почти до лимита 500 символов |
| `in_list` | список значений: `Age IN (...)` |
| `edge_*` | граничные: идентичные (1.0), не пересекающиеся (0.0), пустая аудитория (0.0), полная (1.0) |

Каждый сценарий помечается отдельным именем запроса
(`/getPercent[<лейбл>]`), поэтому в отчёте статистика (RPS, p50/p95/p99,
ошибки) разбивается по типам условий. Ответ дополнительно
проверяется: HTTP 200 и `0 <= percent <= 1`.

## Запуск

Приложение должно работать (`docker compose up`, API на 80-м порту).

### Web UI

```bash
uv run locust -f loadtest/locustfile.py --host http://localhost:80
```

Далее в браузере http://localhost:8089: задать число пользователей и
скорость спавна, Start / Stop.

### Headless (для CI, повторные прогонки)

```bash
uv run locust -f loadtest/locustfile.py --headless \
    -u 50 -r 10 --run-time 60s --host http://localhost:80 \
    --csv loadtest/report --html loadtest/report.html
```

- `-u` — целевое число одновременных пользователей;
- `-r` — скорость спавна, пользователей в секунду;
- `--run-time` — длительность нагрузки;
- `--csv report` — `report_stats.csv`, `report_stats_history.csv`,
  `report_failures.csv`; `--html` — самодостаточный HTML-отчёт.

Полезные флаги: `--only-summary` (только итоговая таблица),
`--json report.json` (полный JSON), `-s 500` (остановиться после
500 ошибок).

## Ориентиры (базовые замеры)

Профиль «20 пользователей, 20 секунд, одна машина, docker-обвязка»:

- суммарно ~128 req/s, 0 ошибок;
- p50 ≈ 100 мс, p95 ≈ 170 мс, p99 ≈ 260 мс;
- самое «тяжёлое» условие — `long_or` (длинный фильтр): p50 ≈ 130 мс,
  остальное ≈ 95–105 мс;
- `/health` заметно быстрее (p50 ≈ 70 мс).

Перед сравнением «было/стало» держать одинаковые `-u`/`-r`/`--run-time`
и состояние БД (данные, кэш планировщика).
