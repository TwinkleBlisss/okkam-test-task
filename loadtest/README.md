# Нагрузочное тестирование (Locust)

Нагрузочный тест `GET /getPercent` и `GET /health` на
[Locust](https://locust.io) (dev-зависимость, ставится через `uv sync`).

## Сценарии

В `locustfile.py` - пул из ~70 пар `(audience1, audience2)`,
**сгенерированных ИИ** (seed=42, воспроизводимый): простые фильтры по
возрасту/полу, комбинации AND/OR, длинные фильтры почти до лимита
500 символов и граничные случаи (идентичные, не пересекающиеся и пустые
аудитории). У каждого сценария свой лейбл - статистика в отчёте
разбивается по типу условия (`/getPercent[<лейбл>]`); ответ
дополнительно проверяется (HTTP 200 и `0 <= percent <= 1`).

## Запуск

Приложение должно работать (`docker compose up`, API на 80-м порту).

```bash
# Web UI: http://localhost:8089 (задать число пользователей, Start)
uv run locust -f loadtest/locustfile.py --host http://localhost:80

# Headless: 50 юзеров, спавн 10/с, 60 секунд; отчёты loadtest/report*.csv и report.html
uv run locust -f loadtest/locustfile.py --headless \
    -u 50 -r 10 --run-time 60s --host http://localhost:80 \
    --csv loadtest/report --html loadtest/report.html
```

## Замеры (2026-11-16)

Отчёты (HTML): 

- `Locust_before_cache.html` (без кэша),
- `Locust_after_cache_on_db.html` (+ кэш результата запроса, `db.py`),
- `Locust_after_cache_on_validation.html` (+ кэш валидации,
`schemas.py`).

Нагрузка наращивалась ступенями: 10 → 20 → 50
пользователей.

| нагрузка | без кэша | + кэш результата | + кэш валидации |
|----------|----------|------------------|-----------------|
| 10 юзеров | ~110 req/s, p50 33 мс, p95 80 мс | ~137 req/s, p50 19 мс, p95 48 мс | ~168 req/s, p50 8 мс, p95 15 мс |
| 20 юзеров | - | ~200 req/s, p50 45 мс, p95 100 мс | ~310 req/s, p50 11 мс, p95 26 мс |
| 50 юзеров | - | ~190 req/s, p50 200 мс, p95 300 мс | ~570 req/s, p50 33 мс, p95 75 мс |

Выводы:

- Кэш запроса к БД конечно ускорил работу, но не очень сильно. На 50  юзерах время ответа стало слишком большим.
- Кэш валидации значительно улучшил ситуацию и даже при 50-ти юзерах p95 < 100 мс
- Самое «тяжёлое» условие, `long_or`, в базлайне заметно медленнее
  остальных (p50 57 мс против ~33) - стоимость росла с длиной
  фильтра; с кэшем валидации все лейблы на одном уровне (p50 17–18 мс).
- Ошибок не было ни в одном прогоне.

Уточнение: данные проверки я проводил просто ради интереса и чистота эксперимента тут не соблюдена (нагрузку менял вручную и в разное время).
